01 · LESS DATA

전체 화면 대신, 바뀐 타일만

1920×1200 화면을 32×8 픽셀 타일 9,000개로 나눕니다. 한 타일이라도 두 성공 이력 중 하나와 다르면 전송 대상으로 선택합니다. 커서의 새 위치를 그리는 일과 이전 위치를 지우는 일을 함께 처리합니다.

첫 두 프레임은 전체 화면입니다. 전송 성공 때 H0/H1을 번갈아 확정합니다. 두 이력 모두 같은 캡처로 안정되기 전에는 같은 위치를 다시 보낼 수 있으므로, 전송 60회가 서로 다른 화면 60장을 뜻하지 않습니다. 그림은 host 이력 규칙을 보여주며 장치 내부 버퍼 구조를 단정하지 않습니다.

정적인 화면은 계속 보내지 않습니다

변경 타일이 없으면 JPEG와 USB 출력을 생략합니다. 두 이력이 안정된 generation은 같은 캡처를 다시 비교하는 작업도 건너뜁니다. 약 1초 간격의 idle 기록은 상태 확인용이며 USB 영상 패킷이 아닙니다.

전체 갱신 옵션도 무조건 매번 전송하지 않습니다

full은 변화가 발견된 프레임의 선택 범위를 9,000타일로 넓힙니다. 변화가 전혀 없는 화면까지 계속 보내는 모드는 아닙니다. 코딩처럼 국소적인 변화에는 delta가 전송량을 줄이는 기본 원리입니다.

02 · WHERE THE WORK GOES

단계별로 줄이는 비용

이 기능들은 서로 다른 병목을 다룹니다. 하나를 빠르게 해도 다른 단계가 오래 걸리면 화면 갱신률은 그만큼 늘어나지 않습니다.

캡처 · 대기열

1. 가장 최근 캡처를 선택

LatestCapture는 처리할 모든 캡처를 줄 세우지 않고 최신 snapshot을 보관합니다. 인코딩·전송이 끝난 뒤 오래된 화면부터 따라잡는 지연을 줄입니다. 도착 알림도 최신 generation을 합쳐 전달합니다.

진행 중인 USB 쓰기를 중간 취소하는 기능은 아닙니다. 캡처 원본을 안전한 Data로 복사하는 작업은 여전히 있습니다.
[S2] Capture.swift · FrameArrival.swift
메모리 · 항상 적용

2. 이미 연속된 픽셀은 공유

BGRA 데이터의 행 간격과 크기가 정확히 맞으면 다시 정렬 복사하지 않고 불변 Data 저장소를 공유합니다. Swift의 copy-on-write로 이후 수정이 기존 이력을 덮어쓰지 않게 합니다. 행 padding이 있을 때만 정렬된 행을 복사합니다.

전체 파이프라인이 zero-copy가 된 것은 아닙니다. SCK 캡처 복사와 Metal 경로의 버퍼 복사는 별도입니다.
[S1] DeltaEncoder.prepare
변경 검사 · CPU

3. 같은 행은 한 번에 건너뛰기

C의 memcmp로 한 행을 연속 비교합니다. 같은 행이면 끝내고, 다른 행에서만 타일 구간을 확인합니다. 알파를 포함한 BGRA를 정확히 비교하며 두 이력의 변경 mask를 OR로 합칩니다.

이전 커서 자리도 변경 영역에 남깁니다. 단순히 새 커서 주변만 보내는 알고리즘은 아닙니다.
[S3] racer_mark_changed_tiles
변경 검사 · 선택 옵션

4. Metal로 두 이력을 병렬 비교

한 타일을 32개의 SIMD lane이 나누어 보고, 각 lane이 8개 행을 검사합니다. simd_any로 변경 여부를 모아 CPU와 같은 mask를 만듭니다. GPU 공유 버퍼는 재사용합니다.

매번 현재/H0/H1 픽셀을 버퍼로 복사하고 GPU 완료를 기다립니다. JPEG는 CPU가 인코딩합니다. M5 통합 메모리만으로 복사·동기화 비용이 사라지지는 않습니다. GPU 사용 자체가 속도 향상의 증거는 아닙니다.
[S4] MetalTileDiffer.changes
JPEG · C 구현

5. 타일별 JPEG와 CPU 병렬화

32×8 타일을 12개의 8×8 Y/Cb/Cr 블록으로 처리합니다. 분리형 DCT, 양자화, Huffman 부호화를 사용합니다. 단색 블록은 일반 DCT를 생략하는 경로가 있습니다. 큰 변경에서는 타일 묶음을 여러 작업에 나누고 마지막에 순서대로 조립합니다.

작업별 고정 출력 구간을 사용해 덮어쓰기를 피합니다. 작은 변경에서는 C 경로 자체도 병렬 실행을 생략합니다. 장치 형식은 JPEG 4:4:4이며 H.264·HEVC·AV1 선택 기능은 없습니다.
[S3] quantize · encode_tile_chunk · encode_parallel
타이밍 · periodic / arrival

6. 누적 대기와 오래된 알림 줄이기

periodic은 단조 시계의 절대 시간표를 사용하고 작업이 늦으면 따라잡기 폭주 없이 기준을 다시 잡습니다. arrival은 처리 시작점의 간격 제한과 새 캡처 알림을 사용합니다. 변경 프레임 대기에는 one-shot strict timer와 semaphore를 씁니다.

busy-wait나 실시간 처리 보장은 없습니다. 타이머 개선으로 USB 전송 간격이 일정해져도 입력부터 패널 발광까지의 지연 개선을 곧바로 증명하지는 않습니다.
[S2, S5] Capture.swift · FramePacer · FrameWaiter
메모리 · 선택 옵션

7. 인코딩 출력 버퍼 재사용

최대 크기의 출력 공간을 매번 새로 할당하는 대신 pool에서 빌립니다. 프레임 Data의 마지막 참조가 해제된 뒤에만 돌려받습니다. 사용하지 않는 버퍼는 패널당 최대 2개를 보관합니다.

2개는 ‘빈 버퍼 캐시’의 상한입니다. 전체 메모리나 살아 있는 프레임이 2개뿐이라는 뜻은 아닙니다. 데이터 수명 때문에 전송 중인 프레임을 덮어쓰지 않습니다.
[S6] FrameBufferPool · Data(bytesNoCopy:)
선행 준비 · 실험 옵션

8. 전송 중 다음 프레임 준비

512타일 이상 바뀌면 별도 작업 하나가 다음 캡처의 비교·인코딩을 시도합니다. 실제 앞 프레임의 정확한 완료 확인과 최신 generation 일치가 모두 있어야 결과를 사용합니다. 늦거나 오래된 결과는 기다리지 않고 버립니다.

실제 비교에서는 출력 속도 향상이 없었습니다. 별도 작업은 최대 하나이며 일반 USB 오류를 재시도하는 기능도 아닙니다. 조건부 구현을 ‘무조건 빠름’으로 표현하지 않습니다.
[S7, E1] FramePreparationPipeline · 실제 USB 비교
전송 전 검사 · 항상 적용

9. 전체 검사를 빠르게 수행

C 검사기는 Huffman의 앞 8비트를 table로 빠르게 판독하고 amplitude를 바이트 단위로 소비합니다. 긴 코드와 짧은 끝부분은 tree를 따라갑니다. 타일 순서·JPEG entropy·stuffing·EOI·footer·길이 검사는 유지합니다.

검사를 생략해 속도를 얻는 방식이 아닙니다. 마지막 Windows 준비 단계에서 과거 fixture의 양성 검사 범위도 보강했습니다. 기존 시험 결과와 보강 후 결과는 구분합니다.
[S8, E4] FrameValidator.c · Windows 준비 시 테스트 보강
패널 · 캡처 버퍼

10. 필요한 화면만 생성

선택한 역할에만 가상 화면과 capture worker를 만듭니다. 자동 CPU 예산은 성능 코어 수를 선택 화면 수로 나눈 뒤 1/2/4/8 중 하나를 고릅니다. queueDepth 2/3/5는 ScreenCaptureKit의 캡처 버퍼 설정입니다.

특정 M5 코어에 작업을 고정하지 않습니다. queueDepth는 USB 출력 대기열 크기가 아니며 커지면 항상 빨라지지도 않습니다. 미선택 패널의 전원을 끄는 기능도 아닙니다.
[S2, S9] SCStreamConfiguration · SessionEngine

04 · NATIVE PATH

0.3.0: Python 중계 비용을 제거

이전 프레임 경로
Swift 캡처·C 인코딩→프레임 pipe→Python worker→C 검사·USB

부모/자식 사이로 프레임 바이트와 완료 신호가 오갔습니다.

현재 프레임 경로
Swift 캡처·C 인코딩→C 검사→libusb 직접 전송→이력 확정

캡처 worker 안에서 직접 처리합니다. 세션 관리는 Swift VerifiedSession이 맡습니다.

프레임 데이터의 프로세스 간 전달과 Python 실행 의존성을 없앴습니다. 가상 화면의 준비·공동 종료에는 작은 제어 pipe를 계속 사용합니다. 이 구조 변경의 실제 USB 속도 향상률은 아직 측정하지 않았습니다. [S11, E3]

실제 성공 확인은 유지됩니다. libusb 반환 코드 0과 요청한 전체 바이트 수가 모두 일치해야 이력을 갱신합니다. 부분 전송·실패는 중단하며, 라이브러리의 전송 완료가 패널에 보였다는 확인이나 장치의 bulk-IN 응답은 아닙니다.
05 · MEASURED, NOT ESTIMATED

옵션을 모두 켜면 더 빠를까요?

9월 11일, 세 화면을 연결한 상태에서 오른쪽 화면만 움직인 실제 USB 비교입니다. 5조건마다 같은 125초 합성 작업을 수행했고, 분석에서는 단계 앞뒤 5초를 제외했습니다. 아래 숫자는 원본 JSON에서 가져왔습니다.

06 · HOW TO READ THE SETTINGS

기능·효과·한계를 함께 읽기

‘60fps 제한’과 실제 60Hz 표시는 같은 뜻인가요?

아닙니다. 현재 가상 화면 생성은 60Hz이고 캡처·앱 제한은 최대 60fps입니다. 캡처 도착률, 같은 generation의 반복, 인코딩·검사·USB 시간, 패널 표시가 각각 다릅니다. 제한만 120으로 바꿔도 새로운 화면 120장이나 물리 120Hz 표시가 보장되지 않습니다. 별도 하드웨어 커서도 구현돼 있지 않아 커서가 캡처 픽셀에 포함됩니다. [S2, S12]

어떤 기능이 선택 옵션이고, 어떤 기능은 항상 적용되나요?

선택 옵션: CPU 작업 수·자동, CPU/Metal 변경 검사, periodic/arrival, delta/full, queueDepth, 버퍼 재사용, 적응형 작업 수, 전송 중 준비, 사용할 화면입니다.

기본 처리 규칙: 최신 snapshot, 두 이력과 처음 두 번의 전체 프레임, 정렬된 Data 공유, 변경 없는 프레임 생략, C JPEG/entropy 검사, 정확한 전송 뒤 이력 확정입니다. 설치 버전 0.3.0의 네이티브 중계 구조도 별도 토글 없이 사용합니다.

모든 코어와 GPU를 쓰면 M5 성능을 최대한 쓰는 것 아닌가요?

목표는 자원 사용률 자체보다 짧고 일정한 반응입니다. 작은 변경은 작업 배분 비용이 더 클 수 있고, Metal 비교에는 복사와 완료 대기가 있습니다. 코어 수 증가는 공유 USB의 전송 용량을 늘리지 않습니다. macOS 스케줄러가 실행 코어를 정하며 이 앱은 성능 코어에 고정 배치하거나 Neural Engine을 사용하지 않습니다.

안정성 장치는 왜 성능 설명에 포함되나요?

잘못된 이력을 다음 프레임의 기준으로 삼으면 커서 잔상이나 화면 손상이 생길 수 있습니다. 정확한 전송 후 이력 확정, 준비 결과의 generation 확인, 첫 두 프레임 후 순차 시작, 모든 캡처 정지 후 공동 종료를 유지합니다. 이는 fps를 높이는 기능보다 정확성과 복구를 지키는 조건입니다.

현재 저장된 옵션이 권장 설정인가요?

저장값은 사용자 선택이며 성능 우승 조합을 뜻하지 않습니다. 과거 비교 후에는 CPU1·버퍼 재사용만 켠 설정을 선택했지만 이후 사용자가 바꿀 수 있습니다. 이 아티팩트는 현재 설정을 수정하거나 특정 조합이 항상 최적이라고 단정하지 않습니다. 한 번에 하나씩 바꾸고 같은 커서·창 이동 작업을 비교해야 합니다.
