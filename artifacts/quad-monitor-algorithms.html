01 · LESS DATA

Send changed tiles instead of the whole screen

Divide a 1920×1200 screen into 9,000 tiles of 32×8 pixels. Select a tile if it differs from either successful history. This both draws the new cursor position and erases the previous one.

Changed = (current ≠ H0) OR (current ≠ H1)

The first two frames are full frames. Successful transfers commit H0/H1 alternately. Until both histories settle on the same capture, the same positions may be sent again, so 60 transfers do not mean 60 distinct images. This illustrates host history rules without asserting the device's internal buffer structure.

Static screens are not sent continuously

With no changed tiles, JPEG encoding and USB output are skipped. For a settled generation, even comparison of the same capture is skipped. Idle records roughly every second report status; they are not USB video packets.

Full-update mode does not force every transfer

full expands selection to all 9,000 tiles when a frame changes. It does not continuously send an entirely unchanged screen. For localized changes such as coding, delta is the basic way to reduce traffic.

02 · WHERE THE WORK GOES

Reducing costs at each stage

These features address different bottlenecks. Speeding up one stage does not raise refresh rates proportionally if another stage remains slow.

Capture · queue

1. Keep the latest capture

LatestCapture keeps the latest snapshot instead of queuing every capture. This reduces the delay of catching up with old screens after encoding and transfer finish. Arrival notifications also coalesce to the latest generation.

This does not cancel a USB write already in progress. Copying captured pixels into safe Data storage is still required.
[S2] Capture.swift · FrameArrival.swift
Memory · always applied

2. Share pixels that are already contiguous

When BGRA stride and size match exactly, immutable Data storage is shared without another repacking copy. Swift copy-on-write prevents later changes from overwriting history. Packed rows are copied only when row padding is present.

The full pipeline is not zero-copy. SCK capture copies and Metal buffer copies are separate costs.
[S1] DeltaEncoder.prepare
Change detection · CPU

3. Skip identical rows at once

C's memcmp compares a whole row contiguously. Identical rows need no further work; only differing rows require tile-range checks. BGRA, including alpha, is compared exactly, and masks from both histories are combined with OR.

The previous cursor position stays in the changed region. The algorithm does not simply send the area around the new cursor.
[S3] racer_mark_changed_tiles
Change detection · optional

4. Compare both histories in parallel with Metal

Each tile is divided across 32 SIMD lanes, each checking 8 rows. simd_any combines the change flags into the same mask as the CPU. Shared GPU buffers are reused.

Current/H0/H1 pixels are copied into buffers on each pass, followed by a wait for GPU completion. JPEG is encoded on the CPU. M5 unified memory does not eliminate copy and synchronization costs. GPU use alone is not evidence of higher speed.
[S4] MetalTileDiffer.changes
JPEG · C implementation

5. Per-tile JPEG and CPU parallelism

A 32×8 tile becomes twelve 8×8 Y/Cb/Cr blocks. Encoding uses separable DCT, quantization, and Huffman coding, with a shortcut that skips general DCT for solid-color blocks. Large changes are divided into tile batches across workers and assembled in order afterward.

Fixed output regions per worker prevent overwrites. For small changes, the C path itself skips parallel execution. The device format is JPEG 4:4:4; H.264, HEVC, and AV1 are not selectable.
[S3] quantize · encode_tile_chunk · encode_parallel
Timing · periodic / arrival

6. Reduce accumulated waits and stale notifications

periodic uses an absolute schedule on a monotonic clock, resetting its reference when late instead of creating a catch-up burst. arrival uses a start-to-start interval limit and new-capture notifications. Waiting for changed frames uses a one-shot strict timer and a semaphore.

There is no busy-wait or real-time guarantee. More regular USB transfer intervals after timer improvements do not directly prove lower input-to-panel-light latency.
[S2, S5] Capture.swift · FramePacer · FrameWaiter
Memory · optional

7. Reuse encoding output buffers

Borrow maximum-size output storage from a pool instead of allocating it each time. Return it only after the last frame Data reference is released. Cache at most 2 unused buffers per panel.

Two is the limit on cached free buffers, not on total memory or the number of live frames. Lifetime tracking prevents overwriting frames in transit.
[S6] FrameBufferPool · Data(bytesNoCopy:)
Speculative preparation · experimental

8. Prepare the next frame during transfer

When at least 512 tiles change, one separate task attempts comparison and encoding of the next capture. Its result is used only after exact completion of the preceding real frame and a match with the latest generation. Late or stale results are discarded without waiting.

The actual comparison showed no output-rate improvement. At most one separate task runs; this is not a retry mechanism for general USB errors. A conditional implementation is not an unconditional speedup.
[S7, E1] FramePreparationPipeline · actual USB comparison
Pre-transfer validation · always applied

9. Speed up complete validation

The C validator uses an 8-bit Huffman prefix table and consumes amplitude bits in byte-sized portions. Long codes and short tails follow the tree. Tile order, JPEG entropy, stuffing, EOI, footer, and length checks are preserved.

Speed does not come from skipping validation. Positive coverage of historical fixtures was also strengthened during the final Windows preparation stage. Earlier results and results after that strengthening are distinct.
[S8, E4] FrameValidator.c · stronger tests during Windows preparation
Panels · capture buffers

10. Create only the displays you need

Virtual displays and capture workers are created only for selected roles. Automatic CPU budgeting divides performance-core count by selected display count, then chooses 1/2/4/8. queueDepth 2/3/5 configures ScreenCaptureKit capture buffers.

Work is not pinned to particular M5 cores. queueDepth is not USB output queue size and is not always faster when larger. Deselecting a panel does not turn off its power.
[S2, S9] SCStreamConfiguration · SessionEngine

04 · NATIVE PATH

0.3.0: Remove Python relay overhead

Previous frame path
Swift capture · C encoding→Frame pipe→Python worker→C validation · USB

Frame bytes and completion signals crossed parent/child process boundaries.

Current frame path
Swift capture · C encoding→C validation→Direct libusb transfer→Commit history

Processing happens directly inside the capture worker. Swift VerifiedSession manages sessions.

This removes interprocess frame-data transfer and the Python runtime dependency. Small control pipes remain for virtual display preparation and coordinated shutdown. The actual USB speedup from this architecture change has not yet been measured. [S11, E3]

Actual success checks remain. History advances only when libusb returns 0 and the entire requested byte count completes. Partial transfers and failures stop processing. Library transfer completion is neither confirmation of panel display nor a device bulk-IN response.

06 · HOW TO READ THE SETTINGS

Read features, effects, and limits together

Does a 60fps cap mean actual 60Hz display?

No. Virtual displays are currently created at 60Hz, and capture/app limits are at most 60fps. Capture arrival rate, repeated generations, encoding/validation/USB time, and panel display are different stages. Raising the cap to 120 alone guarantees neither 120 new images nor physical 120Hz display. There is no separate hardware cursor implementation; the cursor is part of captured pixels. [S2, S12]

Which features are optional and which always apply?

Optional: CPU workers/automatic budget, CPU/Metal change detection, periodic/arrival, delta/full, queueDepth, buffer reuse, adaptive workers, preparation during transfer, and selected displays.

Baseline rules: Latest snapshot, two histories and the first two full frames, shared packed Data, skipping unchanged frames, C JPEG/entropy validation, and history commit after exact transfer. The native transfer architecture in installed version 0.3.0 also has no separate toggle.

Does using every core and the GPU maximize M5 performance?

The goal is short, consistent response rather than utilization itself. Dispatch overhead may dominate small changes; Metal comparison adds copies and completion waits. More cores do not increase shared USB capacity. The macOS scheduler chooses cores; this app neither pins work to performance cores nor uses the Neural Engine.

Why include stability rules in a performance guide?

Using incorrect history as the next frame's baseline can cause cursor trails or corruption. Preserve exact-transfer commits, prepared-result generation checks, sequential starts after the first two frames, and coordinated shutdown after all captures stop. These protect correctness and recovery rather than directly increasing fps.

Are the saved options recommended settings?

Saved values are user choices, not a proven winning combination. After the earlier comparison, CPU1 with only buffer reuse enabled was selected, but users may change it. This artifact does not modify current settings or claim one combination is always best. Change one option at a time and compare the same cursor/window tasks.
