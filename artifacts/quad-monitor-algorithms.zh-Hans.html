01 · LESS DATA

仅传输变化的图块，而非整个屏幕

将 1920×1200 屏幕划分为9,000 个 32×8 像素图块。只要图块与任一成功历史记录不同，就将其选中传输，同时绘制新光标位置并擦除旧位置。

前两帧为完整画面。传输成功时交替更新 H0/H1。在两份历史记录都稳定为同一捕获之前，同一位置可能再次发送，因此 60 次传输不代表 60 张不同画面。本图说明主机历史规则，不推断设备内部缓冲结构。

静止屏幕不会持续发送

没有变化图块时，跳过 JPEG 编码与 USB 输出。对于两份历史记录已稳定的generation，也会跳过同一捕获的重复比较。约每秒一次的 idle 记录用于状态检查，并非 USB 图像数据包。

完整更新选项也不会强制每次传输

full会在发现画面变化时将选中范围扩大到全部 9,000 个图块，并不会持续发送完全静止的屏幕。对于编码等局部变化，delta是减少传输量的基本方法。

02 · WHERE THE WORK GOES

逐阶段降低开销

这些功能针对不同瓶颈。即使某一阶段加速，若其他阶段仍耗时，画面更新率也不会同比提高。

捕获 · 队列

1. 选择最新捕获

LatestCapture保留最新 snapshot，而不是将每次捕获全部排队，减少编码和传输完成后追赶旧画面造成的延迟。到达通知也合并为最新 generation。

这不会中途取消正在进行的 USB 写入。仍需将捕获源复制到安全的 Data 存储中。
[S2] Capture.swift · FrameArrival.swift
内存 · 始终应用

2. 共享已连续排列的像素

当 BGRA 行跨度与大小完全匹配时，共享不可变 Data 存储，无需再次排列复制。Swift 的写时复制可防止后续修改覆盖历史记录。只有存在行填充时才复制为紧凑排列的行。

整个流程并非零复制。SCK 捕获复制和 Metal 缓冲复制仍是独立开销。
[S1] DeltaEncoder.prepare
变化检测 · CPU

3. 一次跳过相同行

C 的memcmp连续比较整行。相同行无需后续处理，仅在不同的行中检查图块区间。精确比较包含 alpha 的 BGRA，并对两份历史的变化 mask 取 OR。

旧光标位置也保留在变化区域中，并非仅发送新光标附近的区域。
[S3] racer_mark_changed_tiles
变化检测 · 可选

4. 使用 Metal 并行比较两份历史

每个图块由 32 个 SIMD lane 分工，每个 lane 检查 8 行。使用simd_any汇总变化标记，生成与 CPU 相同的 mask，并复用 GPU 共享缓冲。

每次仍需将当前/H0/H1 像素复制到缓冲，并等待 GPU 完成。JPEG 由 CPU 编码。M5 统一内存不会自动消除复制与同步开销，使用 GPU 本身并不证明提速。
[S4] MetalTileDiffer.changes
JPEG · C 实现

5. 分块 JPEG 与 CPU 并行

将 32×8 图块处理为 12 个 8×8 Y/Cb/Cr 块，采用可分离 DCT、量化与 Huffman 编码。纯色块有跳过通用 DCT 的路径。大范围变化时，将图块组分配给多个任务，最后按顺序组装。

每个任务使用固定输出区间以防覆盖。小范围变化时，C 路径本身也跳过并行执行。设备格式为 JPEG 4:4:4，不提供 H.264、HEVC 或 AV1 选项。
[S3] quantize · encode_tile_chunk · encode_parallel
时序 · periodic / arrival

6. 减少累积等待与过期通知

periodic使用单调时钟的绝对时间表，任务延迟时重设基准，避免突发追赶。arrival使用处理起点间隔限制与新捕获通知。等待变化帧时使用一次性 strict timer 和 semaphore。

没有忙等待或实时保证。计时器改善使 USB 传输间隔更稳定，也不能直接证明从输入到面板发光的延迟降低。
[S2, S5] Capture.swift · FramePacer · FrameWaiter
内存 · 可选

7. 复用编码输出缓冲

从池中借用最大尺寸的输出空间，而非每次重新分配。只有帧 Data 的最后一个引用释放后才归还。每个面板最多缓存 2 个未使用的缓冲。

2 个是空闲缓冲缓存的上限，并非总内存或存活帧数量的上限。数据生命周期管理防止覆盖正在传输的帧。
[S6] FrameBufferPool · Data(bytesNoCopy:)
提前准备 · 实验选项

8. 在传输期间准备下一帧

当至少 512 个图块变化时，一个独立任务尝试比较并编码下一次捕获。仅当前一实际帧精确传输完成且结果匹配最新 generation 时才使用。迟到或过期结果直接丢弃，不等待。

实际对比未显示输出速度提升。 独立任务最多一个，也不是一般 USB 错误的重试机制。不能将有条件的实现描述为必然加速。
[S7, E1] FramePreparationPipeline · 实际 USB 对比
传输前校验 · 始终应用

9. 加速完整校验

C 校验器通过 8 位 Huffman 前缀表快速解码，并按字节片段消耗幅值位。长码与较短尾部使用树遍历。图块顺序、JPEG entropy、stuffing、EOI、footer 和长度检查均保留。

并非通过跳过校验提速。最后的 Windows 准备阶段还加强了旧 fixture 的阳性校验范围，应区分加强前后的测试结果。
[S8, E4] FrameValidator.c · Windows 准备阶段加强测试
面板 · 捕获缓冲

10. 仅创建所需屏幕

仅为选中的角色创建虚拟屏幕与 capture worker。自动 CPU 预算将性能核心数除以选中屏幕数，再从 1/2/4/8 中选择。queueDepth 2/3/5 设置 ScreenCaptureKit 捕获缓冲。

不会将任务固定到特定 M5 核心。queueDepth 不是 USB 输出队列大小，增大也不一定更快。取消选择面板不会关闭其电源。
[S2, S9] SCStreamConfiguration · SessionEngine

04 · NATIVE PATH

0.3.0：移除 Python 中继开销

旧帧路径
Swift 捕获 · C 编码→帧管道→Python worker→C 校验 · USB

帧字节与完成信号在父子进程间传递。

当前帧路径
Swift 捕获 · C 编码→C 校验→libusb 直接传输→确认历史记录

在 capture worker 内直接处理，由 Swift VerifiedSession 管理会话。

移除了帧数据的进程间传递与 Python 运行依赖。虚拟屏幕准备和协调关闭仍使用小型控制管道。此结构变化带来的实际 USB 提速比例尚未测量。[S11, E3]

保留实际成功检查。 仅当 libusb 返回 0 且完成字节数与请求总数一致时才更新历史。部分传输和失败会停止处理。库报告传输完成，既不表示已在面板显示，也不是设备 bulk-IN 响应。

06 · HOW TO READ THE SETTINGS

结合功能、效果与限制理解设置

60fps 限制等于实际 60Hz 显示吗？

不等于。当前虚拟屏幕以 60Hz 创建，捕获和应用上限为 60fps。捕获到达率、同一 generation 的重复、编码/校验/USB 耗时及面板显示是不同环节。仅把限制改为 120，不能保证 120 张新画面或实际 120Hz 显示。也未实现独立硬件光标，光标包含在捕获像素中。[S2, S12]

哪些功能可选，哪些始终应用？

可选： CPU 任务数/自动预算、CPU/Metal 变化检测、periodic/arrival、delta/full、queueDepth、缓冲复用、自适应任务数、传输期间准备及使用的屏幕。

基本处理规则： 最新 snapshot、两份历史与前两次完整帧、共享紧凑排列的 Data、跳过不变帧、C JPEG/entropy 校验，以及精确传输后更新历史。已安装 0.3.0 的原生传输结构也无独立开关。

使用全部核心和 GPU 就能发挥 M5 的最高性能吗？

目标是短而稳定的响应，而非资源利用率本身。小变化中任务分配开销可能更大，Metal 比较还需复制与等待。增加核心不能提高共享 USB 容量。执行核心由 macOS 调度器决定，本应用既不固定到性能核心，也不使用 Neural Engine。

为何性能说明包含稳定性机制？

将错误历史作为下一帧基准会造成光标残影或画面损坏。须保留精确传输后的确认、准备结果的 generation 检查、前两帧后的顺序启动，以及所有捕获停止后的协调关闭。这些保障正确性与恢复，并非直接提高 fps。

当前保存的选项就是推荐设置吗？

保存值是用户选择，并不代表已证实的最佳性能组合。此前对比后选择了 CPU1 且仅启用缓冲复用，但用户之后可能修改。本解说不会更改设置，也不声称某组合始终最优。应每次只改变一项，并比较相同的光标/窗口任务。
